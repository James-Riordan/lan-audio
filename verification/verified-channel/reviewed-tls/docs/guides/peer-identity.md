# Verified peer certificate fingerprint

After the local records handshake completes, call `try engine.verifiedPeerLeafSha256()` to obtain an owned `[32]u8` SHA-256 of the peer leaf certificate's DER. Through the existing Driver, use `driver.engine.verifiedPeerLeafSha256()` at a serialized completed-handshake boundary. The query neither consumes application records nor exposes a provider certificate pointer. Existing Engine method signatures, Error, Driver layout and package pins are preserved.

A client obtains the server fingerprint only after its configured trust, certificate validity, DNS/IP identity and ALPN checks succeed. A server must configure `require_client_certificate = true` and explicit client trust to obtain a client fingerprint. Successful no-mTLS server handshake does not establish a certified client identity. A client's local completion also does not prove that the server has processed its Finished or accepted its client identity/application policy.

Before local completion the query returns InvalidState. An existing terminal error is returned unchanged. Otherwise, missing verified peer identity, local/remote TLS closing, or reported transport EOF yields PeerIdentityUnavailable. Cancel/deinit returns Canceled unless an earlier terminal error already exists. Digest computation failure is PeerIdentityExportFailed; it does not poison the TLS connection. These extra errors use PeerIdentityError, leaving the old Error vocabulary intact.

The returned bytes are copied snapshots. They cannot be revoked after the application copies them. Bind authorization to a live connection generation; clear your session authorization after cancellation, transport failure, TLS error, close, or replacement. Certificate enrollment, role checks, allowlists, renewal and authorization are application policy. This digest covers the entire leaf certificate, so reissued certificates can have different fingerprints even with the same key. It is not an SPKI hash or chain hash.

The external TCP consumer demonstrates both roles using fixture-only fingerprints. Tests compare against independent Python PEM-to-DER and SHA-256 oracles, exercise both-role mutual TLS, one-byte fragmentation, copied ownership, invalid C output contracts, close/EOF/cancel/timeout/authentication failures and record tampering. The independent Python TLS peer checks the actual C boundary. Digest-provider allocation failure injection remains outside this increment's evidence.

The underlying rules are documented by OpenSSL: [certificate DER digest](https://docs.openssl.org/3.5/man3/X509_digest/), [verification result caveat](https://docs.openssl.org/3.5/man3/SSL_get_verify_result/), and [borrowed peer certificate ownership](https://docs.openssl.org/3.5/man3/SSL_get_peer_certificate/). Native evidence is Windows x86_64 with the exact locked SDK; other platform runtime support remains unqualified.
